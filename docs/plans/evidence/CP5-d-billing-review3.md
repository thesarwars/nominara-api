## 3. [major] hold-and-wait moves to pgBouncer
Chosen option: the second one the finding offers (bound the wait, do not add a role). A separate pgBouncer user for billing writes needs a database role (a schema/migration change the stories do not name) and an ADR; that is left to the owner and said in `pgbouncer.ini`.
- RED: `test/integration/billing-write-pool-pgbouncer.spec.ts` through `startPgBouncerFixture({ defaultPoolSize: 1 })`: a holder keeps the only server connection; the write's BEGIN stayed queued past 15 s (pgBouncer's default is 120 s). Unit reds in `billing-write-pool.spec.ts`. (The RED commit carries a pass-through `inBillingWriteTransaction` so the tests fail on behaviour, not on a missing export.)
- Fix: `docker/pgbouncer/pgbouncer.ini` sets `query_wait_timeout = 5` (GLOBAL: it applies to every client of that pooler, the main pool and the worker too: a client that cannot get a server connection in 5 s is disconnected instead of queued 120 s) and documents the sizing rule. `inBillingWriteTransaction` (used by checkout, credit-pack purchase and add-on intents) sets transaction-local `statement_timeout` 5 s and `lock_timeout` 3 s, maps pgBouncer's wait timeout, a closed connection, 57014 and 55P03 to the retryable 503 `degraded` (`nominara_billing_write_pool_timeout_total`), destroys that connection, and holds an `error` listener while the client is checked out (without it pgBouncer closing the connection raised an unhandled `error` event: seen in the first run of the new spec).
- Sizing rule, stated honestly: the write pool and the main pool both log in as `nominara_app`, so "sum of client maxes per user <= default_pool_size" cannot hold; the guarantee is the bound, not the size. The rule that WOULD make it a guarantee (a dedicated pgBouncer user/pool for the write pool, replicas x 4 <= its pool size) is recorded in `pgbouncer.ini` and needs an owner decision.
- Needs the owner: confirm `query_wait_timeout = 5` as the production value (it also bounds the worker's and the main pool's wait), and decide whether to build the dedicated write-pool user.
