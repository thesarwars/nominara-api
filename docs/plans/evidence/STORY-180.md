# STORY-180 - report artifacts in object storage: evidence and status notes

Owner decision 54 (2026-11-02) answers the story's four open decisions. Built on it:

| Decision | Built as |
|---|---|
| (1) Keep E-0, upload after commit | `ExportService.export` records the row with `object_key = 'pending:<id>'` and registers the upload with `afterCommit`. The upload (`put`, no transaction open) is followed by ONE short tenant transaction that records the real key. No async job. **Round 5 (owner decision 60 (c)): the HTTP export now WAITS for that upload before it answers** (`afterTransaction`, below). |

Migration 0161 adds `report_artifacts.link_token_hash` (SHA-256, unique where set) and `link_revoked_at`. The link lives until the artifact's own `expires_at` (7 days from build). |
| (4) 8 MB = 8,388,608 bytes | `REPORT_ATTACHMENT_MAX_BYTES`. A file of at most that is attached, one byte more is linked. |

## Design points a reviewer should know
- **The link token is derived, not random:** `HMAC-SHA256(HKDF-SHA256(QUEUE_JOB_SIGNING_KEY, salt empty, info "nominara/report-link", 32 bytes), artifact_id)` (no purpose prefix; the purpose is carried by the HKDF info), base64url (43 chars). A cadence delivery that fails is retried with the SAME artifacts and its email must stay byte-identical (Resend refuses a changed body under one idempotency key); a random token cannot be recovered from the stored hash. Only the SHA-256 is stored. The key is an HKDF subkey (info `nominara/report-link`) of the job-signing key, and the hash is written once: if the signing key rotates between a delivery's attempt and its retry, the plan FAILS CLOSED (delivery fails, is retried, settles failed with a notification) instead of overwriting the hash and killing links already mailed. A dedicated non-rotating `REPORT_LINK_SIGNING_KEY` would close that window; it would be a new environment setting, so it is left to the owner (see Open).
- **The route's workspace id is a lookup scope, not a credential.** It selects whose RLS the two statements run under (system actor). A token presented under another workspace's id finds no row. Every refusal (unknown, wrong workspace, revoked, expired, upload never landed, key outside the workspace prefix) is the same 404.
- **The API origin for the link is `OAUTH_REDIRECT_BASE_URL`** (the only existing setting that names the API's public origin). If a dedicated setting is wanted, that is a one-line change in `mailDepsFromEnv`.
- **Known window:** (c) a presign already issued stays valid for its 15 minutes after revocation or workspace deletion; the NEXT click is refused. (The former windows (a) and (b), a failed put or a failed record leaving the row `pending:` forever, are closed by round 5: the row is marked `failed:` and the request answers 503; see Review round 5.)
- **Per-email attachment budget:** the files attached to one email add up to at most 8,388,608 bytes (in order); the rest become links. This bounds the message (base64 adds a third; Resend refuses over 40 MB) regardless of how many projects or formats a report has. The story / reference say "attachment <= 8 MB"; this reads it per email, which the owner should confirm.
- **Credential resolution and presigning never happen inside a request transaction (round 5, ADR-0003).** Storage readiness is a guard (`StorageReadyGuard`, `TenantObjectStore.assertReady()`) that runs BEFORE the transaction opens (round 6: a GLOBAL guard keyed on `@RequireStorage()`, registered before `QuotaGuard`). The download route does its lookup on the ambient client and presigns after the transaction has committed and released its connection (`afterTransaction`). The emailed-link route already presigned after its own short transaction.
- A scheduled email resolves its files once, before the first recipient. A file that never reached storage fails every recipient (nothing is mailed), so the delivery reads `failed` and the cadence path retries.
- Observability: span-shaped log lines `reports.artifact.upload`, `reports.link.resolve`, `reports.scheduled.mail_artifacts` (workspace ID only); metrics `nominara_reports_artifact_uploads_total{outcome}`, `nominara_reports_link_clicks_total{outcome}`, `nominara_reports_mail_artifacts_total{outcome}`.

## Review round 5 (owner decisions 60 and 54)
**(c) The export waits for the upload.** `POST /projects/{id}/reports/export` commits the row, uploads the file after the commit with no transaction open and no pooled connection held, records the stored key in ONE short transaction, and only then answers (`TenantContextInterceptor` runs `afterTransaction` tasks after COMMIT and after releasing the connection; `src/api/after-transaction.ts`). `download_url` works immediately. The 409 / `Retry-After` / poll contract is gone; a stored file that is unavailable (a `pending:`, `failed:` or `purged:` marker) answers 503 `degraded` on the download route. A failed upload answers 503 `degraded` on the export, and the row is NEVER left `pending:`:
- put fails -> the row becomes `failed:<id>`;
- put lands but recording the key fails -> the object is deleted FIRST (no connection held), then the row becomes `failed:<id>`; if the delete fails the row stays `pending:` and the nightly cleanup deletes the object and marks it purged;
- the scheduled (cadence) path is unchanged in shape: `uploaded()` now REJECTS when an upload of this process failed (it remembers a failure for 10 minutes), so a delivery never mails over a file that is not stored, and the `pending:`-but-object-exists fallback in the link route is deleted (nothing needs it).
(SUPERSEDED in round 6, see below: the unit is now committed only when the file is stored.) A PDF's `pdf_exports` unit was committed with the row and NOT returned on a failed upload (a retry under the same Idempotency-Key found it committed and cost nothing more; a retry without a key is a new unit). The audit row `report.exported` is written in the request transaction, so a failed upload still has one (its artifact reads `failed:`).

**(b) Retention.** Queue `report.cleanup` (rollup group, `30 3 * * *` UTC, not tenant-scoped, advisory-locked single flight, owner-connection discovery as `task.resurface`). It deletes the object of every artifact past `expires_at`, and of every `pending:`/`failed:` artifact older than 24 hours (`STALE_UPLOAD_MS`; far beyond a live upload and beyond a cadence job's retry ladder), OBJECT FIRST outside any transaction, then marks the row `purged:<id>` (no schema change: `object_key` is text). A crash between the two is repaired by the next run. An object that cannot be deleted leaves its row unmarked, is counted and fails the job so the retry ladder retries. **A delete on a versioned bucket only adds a delete marker: the bytes of earlier versions stay until the bucket's noncurrent-version expiry rule (infra, STORY-003) removes them.** Workspace erasure: `executeWorkspaceHardDelete` gained an optional `deleteWorkspaceObjects(workspaceId)` hook that runs AFTER the cascade commits (a failure is a named `WorkspaceObjectsLeftBehindError`, recorded in `purge_failures`); `retention.purge` supplies it from the storage configuration through `deleteWorkspaceReports` (purge-side wrapper, explicit workspace id) and the new `PrefixDeletingPort.deletePrefix`, which deletes EVERY version and delete marker under `{env}/{workspace}/` of the reports bucket. STORY-182 (not built) owns the raw and crawl prefixes and the per-capture raw expiry; it reuses `deletePrefix`/`workspacePrefix`. NOTE: the reports bucket layout is `{env}/{workspace}/{artifact}.{pdf|csv}` in its own bucket, so the prefix deleted is `{env}/{workspace}/`, not `{env}/{workspace}/reports/`. With storage not configured `retention.purge` runs without the hook and logs `report_objects_not_deleted` every run (the purge is off by default and cannot complete without a compliance exporter anyway).

**(d) Revocation.** `POST /v1/exports/{id}/revoke-link` (`agency:branding`: owner and admin; a manager, analyst or viewer, scoped or not, is 403 naming the permission; audited as `report_link.revoked`) sets `link_revoked_at` (idempotent: the first time stands) and returns `{ export_id, link_revoked_at }`; 404 for an artifact outside the caller's workspace. The link route then answers 401 `token_revoked` with the message "This link was revoked." instead of the neutral 404. The error taxonomy has no 410, and adding one is a spec change, so the existing `token_revoked` code is used. The revoked answer needs the right workspace id AND the real token; a revoked token under another workspace's id, or one past its expiry, is the neutral 404. Gap: nothing yet LISTS the artifact ids behind a mailed link, so the admin UI cannot find the `id` to revoke for a scheduled delivery (an on-screen export knows its `export_id`); exposing artifact ids on the scheduled-report delivery is a follow-up.

**ISO-31** (`test/isolation/assertions/iso-31-report-link-token-isolation.ts`, registered with a breaker): L1 row-level security alone hides A's token hash from B's context; L2 the service's refusal matrix over every (token, path workspace) pair, plus expired, revoked, revoked-under-another-workspace, forged-key and unknown tokens, and everything presigned stays inside the token's own workspace prefix; L3 the unique index on `link_token_hash`. The breaker replaces the tenant policy with `USING (true)` and drops the index (registry allows one breaker per assertion). Source mutations of the service layers, each run against ISO-31 (logs `s180-r5-mut-*.log`): removing the expiry predicate -> caught (L2 expired token served); removing the revoked refusal -> caught; removing the stored-key prefix check in `relativeKeyFromStored` -> caught (forged key served); removing ONLY the explicit `workspace_id = app.current_workspace()` predicate -> NOT caught, by design: row-level security is the guarantee and the predicate is for the planner (the breaker proves L1 catches a broken policy).

**Observability added:** logs `reports.cleanup.workspace` (workspace ID, counts), `report.cleanup.run`, `reports.link.revoke` (workspace ID only), `reports.export.download`; counters `nominara_reports_cleanup_objects_total{outcome}`, `nominara_reports_cleanup_runs_total{status}`, `nominara_reports_cleanup_skipped_total`, `nominara_reports_cleanup_yielded_total`, `nominara_reports_link_revocations_total{outcome}`, `nominara_reports_link_clicks_total{outcome=revoked}`, `nominara_reports_artifact_uploads_total{outcome=delete_failed|mark_failed_failed}`; span `report.cleanup`.

## Review round 6 (second-engineer audit: the pdf_exports cap)
- **BLOCKER 1, a failed upload used up a PDF unit.** The unit stays RESERVED (QuotaGuard) through the request transaction and is COMMITTED in the same short transaction that records the stored key (`ExportService.upload`). It is RELEASED on `put_failed`, `record_failed` and `orphan_removed` (own connection, `releaseTierCap`; if the release cannot be written the reservation stands until the cycle rolls). The response's `pdf.used` counts this export's still-reserved unit (the response is produced only after the file is stored). `reserveTierCap` now RE-TAKES a released reservation under the same job id (it used to answer `alreadyHeld`, so a same-key retry after a failed upload was free and uncapped); a committed one is still a replay. Tests: a failed upload then a retry under a NEW key leaves `used = 1, reserved = 0`; same-key retry likewise; `usage-tier-caps` re-reserve and refused-at-ceiling cases.
- **BLOCKER 2, readiness ran after QuotaGuard.** `StorageReadyGuard` is now a global guard registered BEFORE `QuotaGuard`, acting only where `@RequireStorage()` is declared (the export route). Unconfigured storage is a 503 with `reserved_value = 0, used_value = 0` and no `usage_reservations` row. `api.module.spec.ts` pins the order.
- **Audit.** The interceptor row is `report.export_attempted` (written in the request transaction, before the upload). The outcome is a second row: `report.exported` (in the record transaction) or `report.export_failed` (own short transaction, `after_state {outcome}`). Both are appended with actor type `user` (an API-key caller is recorded as `user`; the service has no auth-method in its context) and no IP / user agent.
- **`scheduleUpload(awaitInRequest)`** throws when `afterTransaction()` registers nothing. **Upload timing:** the HTTP path starts the upload inside the `afterTransaction` task (no afterCommit, no setImmediate), so put-after-release holds by construction.
- **Cleanup.** A `StorageTenancyError` row is quarantined as `refused:<id>` (counter `nominara_reports_cleanup_objects_total{outcome="refused"}`, error log with the workspace ID only), not retried and not failing the job (`refused` is reported separately from `failed`). "Due" now uses the database clock (`now()`); the handler's `now` option is gone. `isStoredObjectKey`/`storedKeySql` and the cadence reuse query treat `refused:` as a marker.
- **Follow-up only (not built):** workspace-erasure retry. If `deletePrefix` fails after the cascade commits, the erasure is not retried by anything but a manual re-run.


## Review round 7 (round-6 audit)
- **`reserveTierCap` is race-safe on its own.** It takes `SELECT ... FOR UPDATE` on the counter row as a separate statement before the CTE (the CTE's `NOT EXISTS` otherwise reads the reservation from the snapshot taken before the lock wait, so N callers re-taking one released job id all bumped the counter), and the `ON CONFLICT ... DO UPDATE` only re-opens a row that is `released`. The lock lasts to the end of the caller's transaction, so call it inside one. Test: 20 concurrent callers on one released job id add exactly one unit and leave one reservation row (red on the round-6 code: 20).
- **Outcome audit rows name the real actor.** `requestAuditActorOf(req)` (audit.interceptor.ts) is the one mapping (support / api_key / user, support grant id, request id, ip, user agent); `writeAuditRow` and the controller both use it, and the controller hands it to `ExportService.export` on `options.audit`, which carries it on `UploadArtifact`. Integration: an HTTP export (same actor/request id/ua as the `report.export_attempted` row), an API-key export and a support-grant export. No production route sets `authMethod: "apiKey"` or `supportGrant` on this route yet, so those two drive the controller the way the global chain does.
- **Cleanup quarantine keeps the key.** Migration `0162` adds `report_artifacts.quarantined_at`; a tenancy refusal stamps it and leaves `object_key` untouched; "due" excludes it. The `refused:` marker is gone (round 6 was unmerged, so no row carries it). When a workspace has refusals and not one object deleted beside them, that is a configuration mismatch: nothing is quarantined, the rows stay due, the run FAILS (`all_refused`, the job throws).
- **Guard order.** `RateLimitGuard` now runs BEFORE `StorageReadyGuard`, `QuotaGuard`, `DailyCapGuard` and `CreditGuard`; a 429 leaves `reserved_value` at 0. This moves it ahead of QuotaGuard/DailyCapGuard, which `security-and-tenancy.md` section 5's diagram (and EPIC-03's global chain) draw the other way; those two need carrying to the docs repo.
- **Ambiguous COMMIT.** When the record transaction throws, the row is re-read by id before anything is deleted: stored means the export succeeded (counter `record_ack_lost`, object kept); unreadable means nothing is deleted or marked (the nightly cleanup decides).
- **Every non-ok end releases the unit**: the three named paths, an unexpected exception inside the upload (`error`), and any error the export handler throws. The release and the `report.export_failed` row share one short transaction (each under its own savepoint).
- **The HTTP reservation job id is `http:<actorId>:<Idempotency-Key>`** in QuotaGuard and the service (`src/lib/usage/reservation-job-id.ts`), so it cannot collide with another user's key or with `scheduled-report:<id>`. QuotaGuard's only user is this route.
- **Nits.** `report-export-no-storage` asserts the counter row count is 0; `run-scheduled-report.ts` uses `storedKeySql` (and skips quarantined rows).
- **Follow-ups (not built):** (a) show `used + reserved` in the cap response (#8); (b) a stale-reservation sweeper, since a reservation whose request died (process crash between the guard and the settlement) stands until the cycle rolls; (c) the download route and report-link route do not test `quarantined_at` themselves (a quarantined key lies outside the workspace prefix, which they already refuse).
