## Decisions taken (each follows the planner's recommendation unless stated)

1. **Stale versus resolved.** The reference reads, literally, that both are "a later audit does not see the finding". They are told apart by whether the audit COULD look: a finding is `resolved` only when this audit got an answer from the place the finding lives (`inScope`), and `stale` when it did not, in this audit and in the one before it, consecutively. Derived from `aux_audits.excluded_rules`; no new column. Add one sentence to `aux-and-geo-analysis.md` section 3 and `schemas/aux.md` ("The lifecycle"): "`stale` applies when the place the finding lives could not be observed in two consecutive audits; `resolved` needs an audit that observed it and did not find the finding."
2. **A job per qualifying finding, keyed as the reference says (changed in review round 2).** The topology row (`system-architecture.md` section 4) is `taskgen:{project}:{rule}:{fingerprint}` and the plan's AC10 says the same, so the code follows the reference: one `task.generate` job per NEW or REGRESSED finding at or above its threshold, key `taskgen:{project}:{rule}:{fingerprint}` (the fingerprint in hex), pinned exactly in the scenario 11 test. No docs change is needed. Known cost: a finding that regresses a second time reuses its key, so a queue that still holds the earlier job id will not accept it; the daily rollup's un-narrowed `task.generate` is the recovery path. If the architect prefers a per-audit key, that is a one-line change and a topology-row amendment.
2a. **Technical notes.** `src/lib/queue/handlers/task-generate.handler.ts` (now validates against the shared payload contract) and `contracts/tasks/task-generate-job.schema.ts` (`TASK_TRIGGER_KINDS`, an enum pinned equal to the condition kinds) are part of this story; add them to its Technical notes.
2b. **Stale history** reads only audits created strictly before the one running, so a redelivered older job cannot treat a newer audit as its predecessor.
3. **One milestone per finding for ever** (`ux_milestones_source`). A finding that resolves, regresses and resolves again keeps its first pin, because the regression is visible on the finding. A structured_data finding that qualifies for both kinds gets `schema_fixed`. The alternative (change the unique key) is a migration and a decision for the owner.
4. **AUX-R-005 and AUX-R-006 stay in STORY-051.** AUX-R-005 is not evaluated at all (owner decision 2026-10-22). They remain named in `excluded_rules`, so the partial score stays honest.
5. **Not from the reference:** nothing numeric was added. `STALE_AFTER_AUDITS = 2` is the reference's "2 consecutive audits".

6. **Stale keeps scoring (review round 2).** The `crawler_access` subscore and the critical cap read `open + acknowledged + in_progress + regressed + stale` (`SCORED_STATUSES`); a stale finding scores exactly as it did while open. Letting it drop out made an unreachable `robots.txt` lift the cap and read as a fix, the cheap score improvement the story says stale exists to prevent. Add to `schemas/aux.md` ("The lifecycle"): "A `stale` finding still counts toward the subscore and the cap. Only `resolved` and `wont_fix` leave them." No `scoring_version` change: the published number never changed while nothing could be stale before this branch.
7. **Only a 2xx or a 404/410 `robots.txt` observes AUX-R-001 / 002.** Any other status (5xx, 429...) is "could not see it": the finding moves toward `stale` and is not resolved (RFC 9309: an unreachable robots.txt means disallow-all). AUX-R-003 stays covered by any answer. Add one sentence to `aux-and-geo-analysis.md` section 3 next to the stale rule.
8. **Ownership.** STORY-052 owns the `aux_status_change` / `schema_fixed` milestone emitter for AUX findings; STORY-066 must not add a second one (`ux_milestones_source` allows one pin per finding). 052 edits STORY-063's `task-generate.handler.ts` and `contracts/tasks/task-generate-job.schema.ts` (see 2a); land the Technical-notes edit with the docs.

## Not done, and why

- A failed audit (every site file unreachable) does not itself stale anything: it writes no findings and reconciles nothing. It does COUNT as an unobserved audit for the next one, so a site that is fully down for N audits never goes stale while a partly reachable one does. State the asymmetry in `aux-and-geo-analysis.md` as intended, or ask for a stale-only reconcile on that path; it is a wrong-nothing inconsistency, not a wrong state.
- Stale rendering in the client (`AuxSection`) belongs to STORY-094.
