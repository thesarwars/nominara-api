## Review round 1 (carry into STORY-048's technical notes)

- **Our outage is not their absence.** A resolver failure other than ENOTFOUND/ENODATA (ETIMEOUT, ESERVFAIL, ECONNREFUSED), a network error or timeout, or a 5xx/429/408 from the target is an `inconclusive` check outcome. The manual `/check` still reports the reason (the customer retries). The daily sweep records `last_checked_at` and changes nothing else: scope kept, no notification, no audit row. Without this, one resolver outage at 02:20 UTC would de-verify every DNS-verified domain in the fleet. A domain that is inconclusive for good (e.g. a target that 5xx's forever) stays verified and is re-checked every 20 hours; an "N consecutive failures" policy is a product decision nobody has made, so it is not invented here.
- **Concurrency.** `applyCheckOutcome` takes the row `FOR UPDATE` and works out the previous state itself (never from the caller's copy), so a manual check holding a stale row cannot notify a loss the sweep already recorded. `DomainVerificationService.check` does NOT lock before its network wait (a row lock held across an external await would be a KAD-06 violation); the lock inside the transition is what makes it safe. The sweep discards an outcome computed before a newer check (`last_checked_at` later than the sweep's check start).
- The `domain.reverify` span and run log gain `inconclusive`; `nominara_domain_reverify_checked_total` gains the label value `outcome="inconclusive"`.

## Review round 2 (carry into STORY-048's technical notes)

- **Our outage is not their absence, for ALL THREE methods.** Round 1 fixed it for DNS-TXT only. For the well-known file and the meta tag, the guarded fetcher reports every resolution failure as `GuardedFetchRefusal("dns_resolution_failed")`, which the checkers read as a conclusive `fetch_refused`: one resolver outage would have de-verified every file- or tag-verified domain. `GuardedFetchRefusal` now carries the resolver errno (`resolverCode`, never in the message, kept through the redirect-hop relabel). The checkers treat a refusal with any `resolverCode` other than ENOTFOUND/ENODATA as `inconclusive` (the DNS-TXT rule); a policy refusal (private address, port, scheme) has no `resolverCode` and stays conclusive. The customer-facing reason is unchanged (`fetch_refused`). Touches `src/lib/net/guarded-fetch.ts`, which STORY-131 owns: a one-property addition, flagged as a scope signal.
- **One rule for both callers.** `applyCheckOutcome` itself handles `inconclusive`: it records `last_checked_at` and the reason, keeps `verified_at`, never notifies and never audits. A customer who clicks re-check on a verified domain during our outage keeps full scope; the sweep's own branch is gone, so the two cannot diverge. The customer still sees the reason on the state returned.
- **Per-project serialisation.** `applyCheckOutcome` takes `SELECT 1 FROM projects WHERE id = $1 FOR UPDATE` first (`lockProject`), and the sweep takes it before its own row lock, so the order is the same everywhere (no deadlock). Without it two losses on different methods of one project could each read the other as still verified and leave `projects.domain_verified_at` set with every method unverified and nobody told.
- **Timestamps.** The sweep writes the time of its own check (`checkStartedAt`), not the run's start, so a manual check that committed in between is never moved backwards past. The run-level `now` is used only for the due-candidate cutoff.
- **AC9 ("a tag on the wrong page")** is unchanged and the decision is recorded: **keep `tag_absent`** (the plan's option a). The meta-tag instructions already name the exact page, `https://{domain}/`, so a tag placed elsewhere is, from the customer's side, an absent tag at the place we told them to put it; a separate `tag_on_wrong_page` reason would need a crawl of other pages to detect, which a verification check must not do. Evidence: `checkers.test.ts` scenarios 3-5 and the `meta_tag` text of `instructionsFor`. The story's status for AC9 can say "met, on this reading".
- **Isolation pattern, recorded as a decision for the architect and `dangerous-area-auditor`.** NEW-A-13 describes per-project fan-out through signed tenant-scoped jobs. `domain.reverify` instead discovers across tenants on the owner connection (reading `domain_verifications`, nonces included) and writes each outcome with an in-process `withTenantContext` as `nominara_app`, taking the workspace from the database row it just read, not from a verified-signature payload. The write path is tested with RLS live; the workspace cannot come from a caller. It is nevertheless a different pattern, chosen because the daily tick has no tenant to name and fan-out would add a signed job per verified domain for no isolation gain. **Confirm or reject**; rejecting means a fan-out producer plus a tenant-scoped `domain.reverify.project` queue.

### STOPPED FOR THE OWNER: an inconclusive result still has no limit

A domain that answers 5xx/429/408 forever, or times out, keeps `verified_at` forever: a customer who loses the domain keeps full-scope crawls against a site they no longer control, so AC7 is not met for that class of failure. The fix needs a persisted marker (when the first inconclusive result of the current run began, or the last CONCLUSIVE success) and a stated grace period. Nothing in `schemas/projects.md` stores either: `domain_verifications` has `verified_at`, `last_checked_at` and `failure_reason` only. The two schema-free options were rejected: moving `last_checked_at` only on conclusive results contradicts round 1 (the existing outage test and the 20-hour re-check interval rely on it advancing), and encoding a counter in `failure_reason` is a hack. **A schema change the story did not name is a specification gap, and the grace period is a product number**, so it is not decided here. Proposal for the owner: add `inconclusive_since timestamptz` (set on the first inconclusive result while verified, cleared on any conclusive one; expand-only migration, no RLS change), and treat a method as failed once `now - inconclusive_since > 7 days` (NOT FROM THE REFERENCE), applying the normal loss path with one notification. The integration test that runs past the grace period goes with it.
