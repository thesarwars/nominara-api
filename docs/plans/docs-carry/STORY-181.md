## 3. `references/system-architecture.md` §8 — record the AC3 rule and replace "Nothing uses it yet"

Replace the sentence "**Nothing uses it yet:** `StorageModule` is not imported by any application module, … raw captures stay in `answer_captures.payload` (`raw_object_key` is always NULL) …" with: `TrackingModule` imports `StorageModule` (the raw download); the capture worker writes every captured answer as a raw object (STORY-181); the other items stay as listed.

Add a bullet **"Raw captures: dual write, no backfill (STORY-181 AC3)"**:

- The capture step writes the verbatim answer to `{env}/{ws}/{yyyy}/{mm}/{id}.json.gz` AND keeps the same text in `answer_captures.payload` (dual write). The object is the retained verbatim copy that the parser and the raw download read; `payload` serves the result document, L1/L2 reuse and legacy rows. Slimming `payload` to metadata is a follow-up, not done here: it would put S3 reads behind every drawer open and every reuse.
- **No backfill.** A row with `raw_object_key IS NULL` (captured before this story, or a reused row) is read from `payload` by the parser and by re-parse; the raw download answers `404 not_found` for it. The retention window bounds how long such rows exist (30 to 1095 days by plan).
- Object storage not configured: outside production a capture is written WITHOUT an object (the legacy path, counted as `nominara_capture_raw_objects_total{outcome="storage_unconfigured"}`); in production the capture fails closed (`object storage is not configured`).
- A reused (L1/L2) row never gets its own object and is never pointed at its source's object (the source may be another workspace's shared-cache entry).

`capture.execute` is NOT an ADR-0003 violator any more (round 4, 2026-10-26): it is phased (`prepare` reads the run under `FOR KEY SHARE` and checks for a settled cell; `run` makes the vendor call, charges the spend meter and PUTs the raw object with no transaction and no client; `commit` re-reads the run under `FOR KEY SHARE`, takes the cell's advisory lock, inserts the row). `ADR-0003` records it. Two guarantees that the single long transaction gave for free are rebuilt:

- **Reaper vs an in-flight cell (SCANFIX D5).** The run's `FOR KEY SHARE` no longer spans the vendor call. The re-read at commit is where a cell is refused on a run the reaper already finalised and refunded (181-AC1i); the vendor was paid and metered, nothing is written. The reaper's `FOR UPDATE` still waits for a cell that is inside its commit.
- **One delivery per cell (E2E-B6f).** The advisory lock no longer spans the vendor call, so two deliveries of one cell would both pay. `run` takes a 90-second claim on the cache (`SET NX`, value a per-delivery token, key `{ns}:ws:{workspace}:capture-cell:{run}:{prompt}:{engine}:{sample}`); the delivery that loses it throws `CellInFlightError` and is retried by the ladder after the winner committed (it then replays and pays nothing). A claim is released when the attempt fails; after a success it lapses on its own. An unreachable cache fails the attempt (closed): the alternative is a double charge. The advisory lock remains at commit, so a duplicate that gets past the claim (claim expired, cache evicted) still writes one row.

## 5. Known gaps recorded after review round 1 (each needs a named owner story before `RETENTION_PURGE_ENABLED` is turned on)

- **Per-capture raw expiry leaks objects.** `src/workers/rollup/retention.ts` `expireRawCaptures` nulls `raw_object_key` and marks `payload.raw_expired` but does not delete the S3 object; since STORY-181 that key is the only pointer to it. system-architecture.md §8 requires deletion at `retention.raw_captures_days`, which is per plan (30 to 1,095 days) and so cannot be a bucket-wide lifecycle rule. STORY-182 covers only whole-workspace prefix purge. Add per-capture object deletion (a worker-bound `TenantObjectStore.deleteStored`, in an ADR-0003 phase, after commit) to STORY-182's scope. The sweep is off by default (`RETENTION_PURGE_ENABLED`), reachable only through `db:maintenance:sweep`; this is a blocker on enabling it.
- **Orphan objects.** The object is written BEFORE the row, under a key that embeds the attempt's own row id. If the commit then fails (a database error, `ledgerCost`, COMMIT), or a duplicate delivery wins the cell, the object stays: no delete is attempted because the commit phase holds a transaction and a delete is a storage call. The retry mints a new id and so a second object. Bounded to the workspace's own prefix; no row points at a missing object; counted as `nominara_capture_raw_objects_total{outcome="orphaned_by_replay"}` for the replay case. No lifecycle rule exists yet (STORY-003) and it cannot express per-plan retention. Same owner story as the item above (an orphan scan of `raw/` keys with no row).
- **A cell can lose its claim to a dead winner.** If the winning delivery's worker dies mid-call, the claim lapses after 90 s and the next retry (5 s, 15 s, 45 s, 120 s ladder) takes it. The `CellInFlightError` path never writes an exhausted `failed` row, so a cell is never recorded failed because another delivery owned it; if every retry meets a live claim the job reaches the dead-letter queue and the stuck-run reaper accounts for the cell.
- **Storage requests are bounded** (`S3_REQUEST_TIMEOUT_MS` 20 s per attempt, 3 s to connect, `maxAttempts` 3), so a stalled store holds a worker slot for at most about a minute. The SDK default is no timeout.
- **The commit transaction still touches Valkey** (the L1 seed, the progress coalescing key, the parse enqueue). That is unchanged by this story and is not object storage or an engine; NFR-ARCH-04 names "an external service", and the ADR reads Valkey as infrastructure. Say so if the owner reads it otherwise.
