## Decisions taken (each follows the planner's recommendation unless stated)

1. **How a customer gets and regenerates an AUX patch: option (a).** The audit writes it during reconcile and a re-detection with changed content or precondition writes a new row; `GET /patches/{id}` plus the finding's `patch`. No mutating route, so nothing a client sends can become a "copy this" artifact. The cost: a customer cannot ask for a patch to be re-made without a new audit.
2. **Missing fields: option (a)**, an expand migration with typed columns and the immutability trigger.
3. **llms.txt as kind `markdown`, sitemap as guidance.** No new vocabulary: the client's `llms_txt` maps to `markdown` targeting `/llms.txt`. AUX-R-007 is guidance only in v1 (`GUIDANCE_ONLY_RULES`), with no alignment link, because a sitemap fix is not about content.
4. **AUX-R-003 and AUX-R-022 are guidance, not patches** (above).
5. **`page_matches` is computed on read from the latest finished audit** (robots: `aux_audits.robots_hash`; llms.txt absent: `llms_txt_present`); `null` for everything an audit does not record a hash for (every page-level kind until page hashes are audited, an existing-llms.txt replacement). null is "not re-checked", never false.
6. **The alignment link is `{path: '/geo/alignment', target_url}`**, a path, because no client route for the optimizer exists yet. STORY-059 should replace it with the real target.
7. **A named `Allow: /` block wins a tie against `Disallow: /`** (the repo's robots matcher: longest pattern wins, a tie goes to Allow). A block for an agent that inherits the `*` group carries the wildcard's other rules with it, because a named group REPLACES `*` for that agent: otherwise opening `/` would also open the paths the site restricted for everyone. A patch that would not actually open an agent (`Disallow: /*` outranks `Allow: /`) is rejected as `ineffective` rather than offered.
8. **Bounds not from the reference:** `MAX_VERIFIABLE_RULES = 1000` and `MAX_VERIFIABLE_AGENTS = 200` (a robots.txt past them is refused for a patch, not waved through), `MAX_FRAGMENT_CHARS = 200_000`, `MAX_JSONLD_CHARS = 100_000`, `MAX_JSONLD_DEPTH = 10`, `LLMS_TXT_MAX_LINKS = 50`, `MAX_DIFF_LINES = 5000`. The architect should confirm or replace them.

## New dependency (OWNER APPROVAL NOT YET RECORDED: record it in the decisions file before merge)

`parse5@8.0.1` (MIT, zero runtime dependencies beyond `entities`, released 2026-04-19). Chosen over `sanitize-html` because the story requires a HARD ERROR on prohibited markup, not a strip, and `sanitize-html` is a stripper (and brings postcss and htmlparser2 with it). `parse5` is the HTML5 specification's own parse algorithm, so what is checked is what a browser would build, and the tree can be walked and refused node by node.

## Review round 1 — what changed, and what still needs the docs repo

- The section 5 list correction ("fourteen", adding `-003` and `-022`) and the story's AC9/Definition-of-done edit must LAND WITH this branch in the docs repo, not stay as a note: the code follows the section 2 catalog, which disagrees with the section 5 list.
- `llms.txt` patches: none is offered when `/llms.txt` answered an error status other than 404 or 410, or when it is absent but a file sits at `/.well-known/llms.txt` (`llms_txt_present`, which `page_matches` reads, counts both, so the precondition and the judgement would disagree). No schema change.
- The robots access check is bounded at 200 rules and 100 agents (about 48 million matcher calls at worst, down from about 2.4 billion at 1000 and 200). A larger robots.txt gets no patch (`malformed_robots`, counted), never an unverified one. These bounds are not from the reference; confirm them.
- The patch's `reversal`, `preconditions`, `jsonld_blocks` and `risk_flags` columns are parsed with their contract schemas on every read; a malformed row fails the request (500) instead of reaching the wire.
8. **A robots patch opens exactly the tracked paths, and the audit's own evaluator judges it (review round 2).** `buildRobotsPatch` takes the tracked paths the audit judged the file against (today `["/"]`, the one path every audit can speak for). For each AI agent it adds an explicit `Allow` line per tracked path that agent cannot fetch (the root, or a path below it, which also covers an AUX-R-001 `high` path_disallow finding), and the explanation names those paths. After building, the patched file is run through `evaluateRobotsTxt` with the same tracked paths: the rule being fixed must be gone and no AUX-R-001 / 002 finding may appear or get worse, else the patch is rejected as `ineffective`. Before this, an AUX-R-002 patch on `Disallow: /blog` with `/blog/post` tracked swapped a medium AUX-R-002 for a high AUX-R-001. AUX-R-001 is therefore generated at both severities.
9. **A finding serves `patch: null` when its latest patch no longer matches the file** (`page_matches = false`), which is what a refused or empty regeneration leaves behind. The patch is still returned by `GET /patches/{id}`. Add a sentence to the `GET /projects/{id}/aux-findings` row: "`patch` is omitted (null) when the latest patch was made against a file that has since changed".
10. **An `html_fragment` patch sets the review flag** from the same detector as `jsonld` (compliance wording in text or any attribute value; a price/metric/credential `itemprop` or meta name), with `risk_flags: ['claim_requires_review']`. A `markdown` sitemap segment is reduced to one line so an encoded newline cannot start a heading in `llms.txt`.
11. **Future coupling, for the STORY-059 plan:** the `patches_immutable` trigger rejects every UPDATE except `finding_id` going NULL. The optimizer (`applied_node_ids`, alignment columns) must record a change as a NEW row or through an explicit trigger exception in a new migration, never an UPDATE of an existing patch.
